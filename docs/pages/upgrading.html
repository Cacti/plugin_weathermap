Upgrading to 2.0

An upgrade replaces application files; it should preserve your maps, images and monitoring data. Prepare a recoverable backup before replacing anything.

Before upgrading

  1. Record your Cacti, PHP, RRDtool and Weathermap versions and the release/commit you plan to install. A develop checkout may contain changes after a release tag.
  2. Back up the entire plugin directory, including configs, output, uploaded images, custom fonts, INCLUDE files outside that directory and local modifications. Back up Cacti's database using your normal procedure. Keep backups outside the web root.
  3. Check Cacti compatibility and release notes. Coordinate the update with administrators so no one edits maps while files are replaced or migrations run.
  4. Compare local code changes before overwriting them. Preserve custom data, but do not copy old application code back over the new release.

Install and migrate

Replace the plugin's application files with the selected official release, preserving user configuration and assets. The plugin's upgrade path performs schema/configuration work and removes known obsolete application paths through its packaged manifest; it is not a backup of arbitrary local modifications.

Older background/icon paths may be migrated into images/backgrounds/ and images/objects/, with configuration references updated. Ensure the relevant accounts can perform migration, and inspect customised paths and INCLUDE files afterward. Do not move images by hand without updating every reference.

The old cacti-resources/editor-resources and OverLib dependency are no longer the current UI implementation. Do not restore old editor-config.php instructions. Current editor access uses Cacti authentication and permissions.

After upgrading

  • Verify the installed version and enablement in Plugin Management; review logs for migration errors.
  • Refresh the browser so JavaScript and CSS match the new PHP files.
  • Check representative maps, custom images/fonts, included templates, graph links and hover previews.
  • Test one save and Undo/Redo on a disposable map. Confirm rendering under the poller account.
  • Check view-only and management accounts and group/map permissions.
  • Verify asymmetric bandwidth and explicitly set capacities. Existing explicit values are retained on upgrade; 1000M is the implicit default. If you then change map defaults in the editor, recheck asymmetric links as described under default capacity.
  • Review curved comment positioning and font availability. Straight fallback at unsafe bends is intentional.

If rollback is necessary, restore a consistent plugin and database backup as appropriate to the migrations performed. Do not mix arbitrary old PHP files with new JavaScript. Report failures with versions and relevant logs.
